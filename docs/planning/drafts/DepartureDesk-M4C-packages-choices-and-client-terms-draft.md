## Goal and boundary

Staff can assemble an **unpublished Package draft** from exact Service Offer draft or published versions, add a package-only service inline, define Client choices that survive to M5 Client Trip Services, choose bundled or service-sum pricing, and review coherent Client terms. A standalone Service Offer may own the same choice and term templates without any Package.

M4C persists draft Package identity, composition, Package price, choice templates, Client terms, optional date window and explicit sales limits. It integrates the M4B anonymous calculator for the selected composition. **M4D owns** publication and its manifest, immutable published graphs, Sales enabled pause/resume/retire, live selection state, capacity review, and one atomic Package-plus-inline-service publication command. M4C has no publish or sell action, no Client Trip, Hold, Allocation, Charge, posted money, capacity event, or named Traveler.

No ADR 0004 namespace. No Administrator publication override. Never reuse `override_supplier_planning_terms`.

## Staff journey: step 3 within the four-step path

1. After adding/pricing a service, Staff may skip Package assembly for an independently sellable Service Offer. Otherwise choose **Make Package** and name it. Add an existing same-Departure service or **Add service here**, which opens the M4A source form inside the Package and returns with the new package-only service draft (`service_offers.independently_sellable = false`). Do not require a separate catalog visit or a second eventual publication click.
2. Mark included services and genuinely optional choices. Choose **Bundled price** or **Sum service prices**. For a bundle, enter one Package price and permitted named choice adjustments; do not require component Client prices or allocate bundle revenue to suppliers. For service-sum, retain each service's price and apply any named Package discount/surcharge without changing a reusable service's own definition.
3. Define the Package payment schedule once and inspect inherited service-specific terms. Add an explicit Package resolution only where two applicable Client conditions truly conflict. Advanced date windows, numeric sales caps and choice min/max appear on demand. The ordinary Package form has no mandatory cap or policy-resolution panel.
4. Try anonymous examples and see selected services/options, Client total, included/additive adjustments, payment dates or unresolved relative milestones, relevant terms, and qualified scenario economics. Invalid choice, unpriced selected option, conflicting terms, or unsupported date returns to its field without discarding unrelated entries. This remains a **draft review**; M4D adds exact publication validation and live availability.

**Viewer:** Draft Package, choice, and terms UI is `manage_departures` only. Viewers do not read unpublished drafts. After M4D they may read published Client-facing facts. Indicative margin and Supplier cost stay `manage_departures`. Shipped M3 cost-forecast Viewer access is unchanged.

## Package identity and versioned composition

| Fact | M4C contract |
| --- | --- |
| Stable Package | UUID identity, Agency/Departure ownership, Staff display name; no generated reference. Draft version numbers positive, monotonic and never reused. One editable draft per Package, optimistic `lock_version`. No published-current pointer needs to be set in M4C. |
| Package version | Version-owned price method, Client terms, optional local sales dates, optional sales cap, and ordered inclusion/placement links to **exact** Service Offer versions. A draft can be abandoned without deleting the stable Package's retained history. M4D creates successors by independent copy after publication; no live inheritance. |
| Included service link | Same Agency/Departure, exact service identity/version, included versus optional placement and a stable position. A Package draft can reference its own inline package-only service draft or an independently usable service version. Sharing an editable draft across multiple Packages is **prohibited** (database constraint). Only published exact reusable service versions can be shared by multiple Packages. A version edit invalidates/rechecks the Package draft review under optimistic locking; a draft link is never represented as an immutable published pin. |
| Package-only service | Created with the M4A/M4B forms within this Package. Set M4A `independently_sellable = false`. May omit a service price when the bundle provides the revenue (M4B bundled-completeness rule). It is not independently selectable. M4D will publish its version and the Package version in **one** transaction/action. If staff later sell the service independently, use an explicit successor/publication path, preserving old pins. |

Rails validations and PostgreSQL composite ownership/foreign key or targeted constraint trigger reject cross-Agency, cross-Departure, wrong-version and cross-Package draft links even by direct SQL. Use session-derived Agency, `manage_departures`, scoped lookups that return unauthorized IDs as not found, and the M4A lock order (Agency, actor, Suppliers in UUID order when any M3 row is locked, Departure, Arrangement/source, then Package/Service Offer).

**Idempotency:** Composite inline-create uses `AgencyCommandIdempotencyKey` with a command name **distinct** from M4D's later publish key. Same-key retry returns the same Package/inline-service draft and cannot leave a stray service draft or double inclusion. Concurrent edits return a recoverable conflict with no half-linked child.

## Client choice templates

A choice group belongs to an exact **Service Offer version**, whether standalone or included in a Package. The Package owns only the placement/inclusion of that version and any narrow version-owned price/term resolution; it does not replace the service's choice template. Define a group name, minimum and maximum selections, stable ordered option identities, and optional Client-visible descriptions. `0..1` is optional one, `1..1` is exactly one. Do not demand a choice group on every service.

Each option must identify exactly what changes when selected: its Service Offer source path/fulfillment binding, named Client price effect, and scoped terms. No nested Service Offer or Package graph is needed for one choice. A missing mapping or ambiguous combination is incomplete. Separate the **Client's option** from M4A's Staff-selected alternative Supplier binding: selecting a dinner option is Client choice; choosing one eligible supplier for a fixed dinner option is fulfillment choice. An option may have no extra price when an explicit included-price rule establishes that result; an unknown surcharge is never silently zero. Ensure one selected Client option maps to one intended source path and that required sources are counted once.

For the Vineyard sketch, create a **Dinner Service Offer** template with exactly one of Standard and Deluxe. Their M3 sources remain **two distinct Arrangement Items**. Standard included and Deluxe surcharge are a *choice shape* from the fixture; the actual Client surcharge and any unconfirmed Supplier facts must be supplied or left as visible draft blockers. A Package includes the Dinner Service Offer once. M5 receives the exact group/options and selected dinner on its Client Trip Service; a standalone dinner service would carry the same template without a Package. M4C does not create an M3 Supplier-side choice or a named Client selection.

At draft review validate `0 ≤ min ≤ max ≤ option_count`, unique option identities, usable mapping for every option and at least one **structurally valid** combination. Current numeric Pool shortage does not make the structure invalid or block future M4D publication. Anonymous preview names the chosen options and one explicitly selected fulfillment path per alternative group, counting no unselected option. M4D will recheck source lifecycle and live feasibility; M5 snapshots and transactionally rechecks the eventual selected choices.

## Package price integration

| Mode | Authority and evaluation |
| --- | --- |
| Bundled | One Package-owned Client price definition evaluated with M4B typed rules. Included package-only components need no service price; optional selections can carry explicit named adjustments. Vineyard `P` per person and single supplement `round_minor(P × s)` stay **Package revenue**; one supplement for the same commercial reason cannot also be charged at lodging service level. The Vineyard `s = 1.0` is **illustrative**, and `P` is unresolved. No artificial allocation across suppliers. |
| Service-sum | Sum only selected Service Offer prices plus named Package adjustments in explicit order/rounding. A reusable Service Offer's price does not change when placed in a Package. An unpriced selected component makes the total incomplete; unselected optional prices do not contribute. |

Both modes use the Departure operating currency and M4B's exact component-level `half_up` rounding; persisted monetary definitions are `bigint` minor units and retain the M4B Departure currency guard. Included tax is displayed without adding it twice. Package-only price definitions are version-owned and use the same calculator contract, not a second formula language. A selected option's price effect is visible as a distinct line, not hidden in a Supplier cost.

## Client terms: one ordinary schedule, scoped exceptions

| Kind | Draft rule and preview behavior |
| --- | --- |
| Payment schedule | One structured Package Client schedule is the default for a bundle; standalone service uses its own schedule. A service in a Package adds an extra **service-specific** condition only when it applies, without restating the whole Package schedule. Fixed dates or explicitly named relative milestones, amount or percent of a stated selected Client price base, due ordering and rounding must be recorded. A relative date that needs an unknown future event remains a conditional term in M4 preview; no due Charge is posted. Do not derive a Client deposit from an M3 Supplier Deposit Requirement. |
| Cancellation | Ordered Client date/threshold tiers may state fixed amounts or percentages with explicit bases; a condition requiring judgment is marked **manual review**. Preview examples may compute only a determinate selected tier. An unresolved/manual outcome is unknown, not zero, and M7 later owns actual cancellation cases and credits. |
| Eligibility and acknowledgment | Structured eligibility and material-term acknowledgment requirements are Client-facing templates for M5 snapshot/revalidation, never inferred from Supplier planning. No Traveler assignment or actual acknowledgment in M4. |
| Scope and conflict | Package terms govern bundled Client price/payment by default; included service terms add only service-scoped conditions. If both state an incompatible rule for the same scope, show the original texts/sources and require an explicit version-owned resolution selecting the governing Client rule and reason. Ordinary nonconflicting inheritance requires no extra form or resolution. Do not silently pick the stricter or broader term. |

Rules must remain explainable in one combined review. Validate monetary schedule components in currency and round each specified line consistently with M4B. Reject unsupported triggers, contradictory tiers, gaps that make a required scenario unknowable, percentage schedules whose base is unspecified, and resolutions pointing to missing terms. Do not require a fully calculable amount for a clearly disclosed **manual-review cancellation clause**; distinguish it from an incomplete computable rule. The M4C preview does not issue invoices, schedule jobs, or make payment/commission assertions.

## Optional sales window and limits

- **Sales window:** Optional local **date** range in the Departure's stored IANA zone (`departures.time_zone`). Both dates inclusive at the business level (start of first date through end of last date); compare later instants as `[start at local midnight, next-day local midnight)` so daylight-saving days are handled by the zone, not a fixed 24-hour duration. A missing zone can be carried on a **draft** Departure. An **active** Departure already has a recognized zone (`ActivateDeparture`). M4D publication requires an active Departure, so a published window always has a zone. Timed-to-the-minute sale deadlines require a later accepted extension.
- **Caps:** Optional numeric Package cap and optional standalone/service cap, each with an explicit basis (`package_bookings`, `persons`, or `resource_units` only where meaningful). **Do not** equate Pool `traveler_positions` with `persons`. A Package booking counts once for Package-booking basis; its included service counts selected service quantity under that service's basis; optional services count only when chosen. No implicit conversion between persons and rooms. Caps are additional commercial limits and are never required just because a Pool is nonnumeric. If Supplier Pool capacity alone governs supply, the cap field stays empty.
- **Stacking:** Anonymous preview can check a scenario's quantity against each configured Package/service cap and applicable numeric Supplier supply separately; the tightest applicable condition governs and all reasons remain visible. **M4 has no Client demand ledger**: it cannot assert remaining headroom after real sales or decrement caps. M5 defines transactional consumption/release with Holds and Allocations under an accepted lock order. M4D will own the time-labeled live selection state; M4C shows only draft rule consequences.

## Commands and integration

Add draft Package create/edit/abandon, include/reorder service, inline package-only service setup, price-method/Package price edits, Service Offer choice-group/option edits, scoped terms and optional cap/window edits. Each mutates one Agency/Departure-scoped draft graph under expected versions. Audit actual M4C actions with new `Package` subject and bounded details; extend closed subject/action catalogs in the implementing change. Do not place a full term graph or anonymous scenario in audit details.

M4C does not change Supplier inactivation, Arrangement ending or M3 Needs-attention catalogs. Draft links may be cleaned up under normal constraints; published pins and their lifecycle consequences begin in M4D. Do not add offer panels to `docs/ui/interface-contract.md` until the implementing slice ships UI. Terminology for Package versus Service Offer is already in `docs/terminology.md`; do not claim publication is shipped.
